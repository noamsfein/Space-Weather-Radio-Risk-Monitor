Data explainer: Kp is a 0-to-9 index that summarizes how disturbed Earth's magnetic field is on a global scale. A higher value means stronger geomagnetic activity, which can interfere with high-frequency radio propagation. It is not a direct measurement of one radio station, and our project does not forecast future Kp.

[Sources] NOAA SWPC planetary K-index endpoint; DATA_SOURCE.md; representative_event.json. Data explainer: The real source is NOAA's Space Weather Prediction Center. Its public JSON endpoint provides preliminary estimated planetary Kp values and timestamps, updated roughly every minute. NOAA derives Kp from magnetic-field observations; the one-minute feed is a frequently updated estimate, not a new independent global measurement every minute. We use time_tag to identify when the estimate applies and estimated_kp as the value used by our rolling-window rule. The producer converts those raw fields into our four-field Kafka event by renaming estimated_kp to kp_value and adding source and ingested_at.

Noam · 1:05, then hand off to Niki. Follow the 6.3 event through each box. Explain the one-topic/one-partition choice. [Sources] Implemented repository architecture; README. Data explainer: Kafka does not change the Kp value or decide whether conditions are risky. It receives each validated observation as a separate message, stores the messages in order in kp_observations, and lets the consumer read them independently. Our Python consumer performs deduplication, calculates the rolling 15-minute maximum, checks for a crossing of Kp 6, and writes the output artifacts. More specifically, during the required demo, `src/replay_producer.py` is the producer: it reads and validates the nine JSONL observations and publishes each row as its own Kafka message; `src/live_poller.py` is the optional producer for current NOAA observations. The Kafka broker running in Docker buffers those messages in the `kp_observations` topic, preserves their partition order, and makes them available to an independent reader; it does not transform the data. `src/stream_processor.py` is the consumer: it reads the Kafka messages and uses `src/processor.py` to deduplicate, calculate the rolling maximum, and decide when an alert should be emitted.

Lesson, limitation, and next step

Deterministic replay made the streaming behavior provable

What we learned

Quiet live data could not demonstrate a threshold crossing. A labeled replay reliably proves crossing, deduplication, window expiry, and rearming.

Limitation

This is a recent global Kp condition - not a forecast or station-level propagation model.

Realistic next step

Add a long-running consumer that continuously processes live NOAA events and refreshes the UI.

The result is small, explainable, and reproducible: one ordered stream, one clear rule, and evidence for every alert.
