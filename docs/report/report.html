1. Problem and useful result

Amateur-radio operators depend on high-frequency (HF) propagation, which can degrade during geomagnetic storms. NOAA publishes an estimated planetary K-index (Kp) roughly every minute, but an operator does not want to watch a feed; they want one machine-readable signal when conditions cross into storm territory. Kp 6 corresponds to a G2 geomagnetic storm, a level at which NOAA notes HF propagation can fade at higher latitudes.

The product is deliberately narrow: one data source, one Kafka topic (kp_observations), one canonical event contract, a rolling 15-minute event-time maximum, and one deterministic alert rule — emit an alert when the rolling maximum crosses from below 6 to at-or-above 6, and rearm only after it falls back below 6. It does not forecast, does not model a specific station or location, and never lets AI decide anything about the alert.

The observable result: replaying the project's labeled nine-event fixture through a real local Kafka broker produces exactly two alerts in outputs/alert.json. The first is:

2. Data source and event contract

The source is the NOAA/NWS Space Weather Prediction Center public JSON service https://services.swpc.noaa.gov/json/planetary_k_index_1m.json — public HTTPS, no key, no personal data, public-domain NWS terms with attribution. Its documented limitations shaped the design: the values are estimated and preliminary (not independent one-minute measurements), they may be revised or missing, planetary Kp is global rather than location-specific, and the feed is often quiet. Dated source checks on both August 11 and August 12, 2026 found 358 well-formed, unique, ordered records at one-minute cadence — and a maximum Kp under 3.5. A quiet live feed cannot demonstrate a Kp 6 alert, which is why the required review path replays a committed, clearly labeled synthetic threshold fixture instead of live data.

Raw-to-canonical mapping and validation

A raw record has four fields (time_tag, kp_index, estimated_kp, kp). Normalization keeps time_tag, renames estimated_kp to kp_value, and adds provenance and ingestion time. Every event — cached NOAA or replay — must pass the same Pydantic contract (src/contract.py): timestamps parse and normalize to UTC (NOAA omits the Z; the documented source convention is UTC), kp_value is numeric, finite, and in [0, 9], and source must be either the NOAA endpoint or the synthetic fixture identifier — anything else is rejected, so synthetic data can never masquerade as NOAA history. The model is frozen and forbids extra fields.

Rolling window and crossing logic

Processing is pure Python, independent of Kafka (src/processor.py), which makes the logic directly unit-testable. The window is event-time based and inclusive: an observation exactly 15 minutes old is still in the window; one second older is not. Duplicate time_tags and late (out-of-order) events are counted and skipped without touching window state — a skipped record can never create, suppress, or rearm an alert. The alert is edge-triggered on the rolling maximum with hysteresis-by-rearm: sustained elevation emits nothing new until the maximum has fallen below 6.

Why one topic on one local Kafka broker

The planetary Kp series is a single global sequence, so one topic with one partition and a constant key is the design that preserves order without ceremony. Kafka still earns its place: it decouples the validated producer from the consumer, gives replayable offsets, and makes duplicate handling observable. A local Docker broker (official apache/kafka image, KRaft mode) keeps the demo reproducible for any reviewer; the demo script recreates broker state on every run precisely so no run can silently reuse stale topics or consumer offsets. The producer is idempotent with acks=all; the consumer uses a fresh group id per run, a bounded idle timeout, and skips malformed messages with a visible warning instead of crashing.

4. Evidence, bounded AI, and reproducibility

Validation and evaluation results

  • Automated tests: 141 passed (contract, processor, outputs, briefing, evaluation, demo fixtures), plus 3 opt-in Kafka integration tests, all passing against a clean Docker broker.
  • End-to-end acceptance: ./run_demo.sh verifies the generated artifacts field-by-field against the committed oracle data/fixtures/replay_expected.json — 9 messages consumed, 8 unique, 1 duplicate skipped, exactly 2 alerts at the labeled timestamps — then runs the full test suite; three consecutive runs passed identically, and a deliberately broken run exits nonzero.
  • Evaluation evidence: python -m src.evaluate regenerates evaluation/evaluation.json deterministically (byte-identical across runs, no network, no key): 7/7 assertions — the replay alert comparison plus six fixed AI-briefing cases.

Bounded AI and its verification

The language model (OpenAI gpt-5-nano, optional) sees only five already-calculated facts — latest Kp, rolling maximum, UTC window start/end, and the rule-based label — and may only phrase them as a two-sentence briefing. It cannot trigger, suppress, or relabel an alert. An automatic validator rejects any candidate containing a Kp number not in the input, a mismatched label, unsupported causes/locations/recommendations, more than two sentences, or empty output, and records the explicit rejection reason; a rejected candidate is never silently repaired. The six committed evaluation cases (correct, wrong number, wrong label, unsupported detail, too long, API unavailable) all produce their expected decisions. With no key, a failed request, or a rejected response, a deterministic two-sentence template built from the same facts writes briefing.txt — the fallback is the required path, not an error state. Full disclosure of runtime and development AI use is in AI_USAGE.md.

Limitations and next step

Limitations. The alert reports a recent estimated global Kp condition; it is not a forecast and not a station-level propagation model. NOAA's one-minute values are preliminary and revisable. The 15-minute window and Kp 6 threshold are a course-scale streaming rule, not an official alerting algorithm. The AI validator checks facts, sentence count, and banned unsupported details — it cannot prove a briefing is well-phrased, and a candidate could avoid banned terms yet still mislead, which is why rejection defaults to the deterministic fallback. The demo replays a labeled synthetic fixture because quiet live data cannot demonstrate the threshold crossing.

One realistic next step. Add the deferred 60-second live NOAA poller (src/live_poller.py). The contract, topic, consumer, and outputs need no changes — normalization from raw NOAA records is already implemented and tested — so the work is confined to scheduled fetching, unseen-time_tag filtering, and failure logging, with the cached replay kept as the reviewer path.
